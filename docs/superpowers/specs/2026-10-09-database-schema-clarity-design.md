# 数据库结构清晰化设计

## 目标

以用户提供的现有表清单为基准，统一举报记录入口，明确物理外键与逻辑引用，修正梗与标签关联表的数据类型和约束，并为冗余计数、软删除记录定义核对口径。所有变更通过 Flyway 迁移落地；不连接或修改正在运行的数据库。

## 设计决策

1. `community_report` 是唯一业务举报表。升级时把 `meme_report` 中尚未进入统一队列的梗举报补入 `community_report`，随后将旧表重命名为 `meme_report_archive` 保留历史；应用代码只保留统一举报实体和 Mapper。
2. `meme_tag_relation.meme_id` 使用与 `meme.id` 一致的有符号 `BIGINT`，`meme_tag_id` 使用与 `meme_tag.id` 一致的有符号 `INT`。迁移清理失效关联行后建立两个级联外键。
3. 点赞和收藏服务都在原记录上切换 `is_deleted` 状态，因此数据库唯一键改为 `(user_id, meme_id)`。若旧数据同时存在有效行和已删除行，迁移保留有效行；仅有已删除行时保留该行，供服务重新启用。
4. `meme` 和 `user_stats` 的计数列统一为 `NOT NULL DEFAULT 0`。迁移仅把 NULL 归零，不猜测或覆盖当前计数；只读核对脚本提供可重算计数的明细口径。
5. 当前截图中的 `meme_report`、`community_report` 都存在，因此迁移以二者均存在为前置条件。迁移不删除举报历史，也不改用户 API 路径。
6. 通知目标、举报目标、用户与内容等跨业务模块 ID 是逻辑引用；多态字段不设置外键。ER 说明将列出当前真实外键和逻辑引用，并注明未来拆库时需要移除的跨模块约束。

## 验收标准

- Flyway 新迁移在迁移目录和目录测试中注册。
- 唯一举报表为 `community_report`；旧表保留为 `meme_report_archive`，无应用 Mapper 继续读写旧表。
- 标签关联字段与目标主键类型一致，失效关联清理后有两个数据库外键。
- 点赞、收藏的当前状态受 `(user_id, meme_id)` 唯一键保护，迁移不会丢弃有效行。
- 冗余计数及软删除的明细来源、可重算方式和不可重算字段均有中文说明。
- 后端测试通过；迁移 SQL 未在用户运行数据库上执行。
