# 已发布梗编辑与审核设计

## 目标

允许作者修改自己已发布或主动下架的梗，同时继续执行内容审核。提交修改后，已发布梗继续展示当前审核通过的旧版本；审核通过后才将修改内容替换为正式内容。审核驳回时保留旧内容，避免用户因一次修改而丢失线上内容。

## 当前项目约束

- 用户发布入口位于 `PublishMeme.vue`，字段包括名称、介绍、封面、标签、媒体资源和结构化链接；发布接口是 `POST /v1/memes`。
- 用户梗接口集中在 `MemeController`，目前提供发布、主动下架、重新上架和永久删除，没有作者编辑接口。
- 梗状态为：`1` 正常、`2` 首次审核中、`3` 主动下架、`4` 永久封禁/彻底删除、`5` 风控锁定、`6` 恢复审核中。公域按梗主表状态决定可见性。
- 管理端现有梗审核以 `meme.status` 为队列依据，审核入口位于 `AdminMemeController` 和管理端梗列表页。因此编辑稿需要独立审核队列，不能把正在公开的原梗直接改成状态 `2`。
- 梗资源和标签分别保存在 `meme_resource` 与 `meme_tag_relation`；浏览、点赞和评论计数保存在 `meme` 主表。

## 方案选择

采用“独立修改稿”方案：正式梗记录始终保存当前已审核版本；用户编辑时创建一条修改稿，管理端审核修改稿。通过后事务性替换正式内容，驳回后正式内容保持不变。

直接覆盖正式记录并改为审核中虽然改动较少，但会让已发布梗在审核期间从公域消失，也无法可靠恢复被驳回前的内容，因此不采用。

## 用户操作与状态规则

1. 作者在自己的主页梗卡片菜单选择“编辑”，编辑表单使用现有发布表单的字段与校验，并通过梗详情接口预填当前正式内容。
2. 只允许状态 `1`（正常）和 `3`（主动下架）提交编辑。状态 `2`、`6` 已有审核中的变更，不允许再创建新修改稿；状态 `5` 沿用现有整改申诉路径；状态 `4` 不可编辑。
3. 同一条梗最多有一条 `PENDING` 修改稿。提交期间再次打开时显示“修改审核中”，不可重复提交。
4. 状态为 `1` 的梗提交修改后仍以旧版公开展示；状态为 `3` 的梗仍保持下架。审核通过仅更新内容，不改变当前可见性状态；作者可在之后使用既有重新上架操作。
5. 审核驳回不修改正式梗、资源、标签或统计数据。作者可查看驳回说明，修改后重新提交。
6. 管理员将梗锁定或永久删除时，安全状态优先。审核操作不得把状态 `5` 或 `4` 改回公开；失效修改稿应被取消或拒绝处理并留下原因。

## 数据模型

新增 `meme_edit_revision` 表。每条记录保存一次修改内容快照及审核记录；审核完成的记录保留，供作者和管理员追踪结果。`content_json` 保存完整可编辑内容，包括 `name`、`introduction`、`image`、`tagIds`、`resourceUrls` 和 `resources`，由服务层校验结构并做版本兼容。

建议字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 修改稿主键 |
| `meme_id` | 被修改的梗 ID |
| `editor_user_id` | 提交修改的作者 ID |
| `base_content_hash` | 提交时正式内容的 SHA-256，用于检测管理员或其他流程造成的内容冲突 |
| `content_json` | 修改内容快照，MySQL JSON 类型 |
| `status` | `PENDING`、`APPROVED`、`REJECTED` 或 `CANCELED` |
| `review_note` | 管理员驳回或取消说明 |
| `reviewed_by` | 审核管理员 ID |
| `created_at` | 修改稿提交时间 |
| `reviewed_at` | 修改稿审核完成时间 |

迁移脚本中每列必须使用中文 `COMMENT`。通过事务锁定 `meme` 主记录后检查是否已有待审修改稿，以保证同一梗只有一条待审版本；不要依赖 MySQL 不支持的部分唯一索引。

## 接口与后端职责

- `GET /v1/memes/{memeId}`：复用现有梗详情读取能力；服务端在作者身份验证后返回本人可编辑状态下的完整资源和标签信息。
- `PUT /v1/memes/{memeId}`：新增作者编辑接口。请求体复用发布内容字段，但后端仅接受白名单内容字段，从认证上下文读取作者 ID，并执行状态、所有权、标签、资源和长度校验。返回修改稿 ID、审核状态和提交时间。
- 个人发布列表增加待审修改稿摘要（状态和提交时间），让作者在卡片上看到“修改审核中”或审核结果；不覆盖正式梗的 `status`。
- 管理端增加修改稿分页、详情和审核动作接口。详情同时展示正式版本与修改版本，明确标出变化字段；驳回时要求填写原因。此队列独立于首次发布与恢复审核队列。
- 修改稿审核通过由独立应用服务在单个数据库事务内完成：重新校验待审状态和 `base_content_hash`、校验标签、更新 `meme` 的可编辑字段、替换标签关系和资源关系，并将修改稿置为 `APPROVED`。不得写入客户端提供的作者、状态、计数、梗 ID 或发布时间。
- 发生正式内容哈希冲突时不覆盖新内容，审核动作返回明确冲突，并要求管理员刷新后重新处理。

## 资源、计数和缓存

- 用户新上传的媒体在修改稿提交时按现有 OSS 发布链路转为可长期访问的正式对象，保证待审期间资源不会过期。
- 驳回或取消后，事务提交后异步清理仅由该修改稿新增且未被正式版本复用的 OSS 对象；通过后异步清理被替换且未被新版本复用的旧对象。删除失败记录日志并允许后续清理，不影响数据库审核结果。
- 审核通过保留 `meme.id`、`user_id`、`release_time`、浏览量、点赞数、评论数及评论、收藏、点赞关系。
- 标签计数按旧标签和新标签的差集增减，避免重复累计；清理梗详情、个人发布列表、首页/搜索相关缓存，并刷新依赖正式内容的索引或缓存。
- 审核通过或驳回后更新作者可见的审核结果，并通过站内通知告知结果与驳回原因。

## 前端交互

- 仅在本人主页对应梗卡片的“更多操作”菜单显示“编辑”。状态不符合规则时隐藏或禁用并显示原因。
- 复用发布表单的控件和校验，标题改为“编辑梗”，提交按钮改为“提交修改审核”；保留用户当前的封面、媒体、标签和链接。
- 提交前说明：“修改审核期间，其他用户仍会看到当前版本；审核通过后展示修改内容。”
- 提交成功后回到本人发布列表并刷新修改审核标记；提交失败保留本地表单内容。
- 审核通过/驳回时刷新状态并展示通知。驳回时保留正式版本，并提供查看原因和再次编辑入口。

## 错误处理与并发

- 不存在、非本人、状态不可编辑、已有待审修改稿、标签失效、资源非法和内容冲突分别返回明确业务错误，不泄露其他用户的私有内容。
- 写入和审核都采用事务；审核动作通过条件更新或行锁保证只能完成一次。重复点击不会重复修改标签计数、删除资源或发送结果通知。
- 若提交后管理员已将正式梗锁定或永久删除，修改稿不能恢复其公域可见性；该稿自动取消或在审核时拒绝，并保留审核记录。

## 验收标准

1. 作者可从本人主页编辑状态为 `1` 或 `3` 的梗；他人不能编辑。
2. 一条梗无法同时存在多条待审修改稿；审核中的梗和锁定/删除的梗不能绕过现有状态规则。
3. 修改审核期间，状态 `1` 的正式旧内容仍公开可见；状态 `3` 仍然下架。
4. 通过后，正文、封面、资源和标签同时替换；梗 ID、发布时间、互动计数、评论和收藏关系保持不变。
5. 驳回后旧内容完整保留，作者可以看到驳回原因并重新修改。
6. 审核通过或驳回的重复请求不重复改动数据；内容哈希不匹配时不会覆盖正式内容。
7. 后端测试覆盖所有权、状态矩阵、重复待审、通过、驳回、冲突、资源与标签替换；前端构建和管理端构建通过。

## 本阶段范围

包含用户编辑入口和表单、后端修改稿 API 与存储、管理端修改审核队列、审核结果通知、数据库迁移及相关测试。不新增微服务或外部依赖，不实现任意历史版本回滚；审核完成的快照仅用于审核记录与追踪。
